### 8.5 Night: HelixDB in-process fake — 31 skips eliminated

33 tests in the suite skipped on every CI run because they
required a running HelixDB gateway on `localhost:6969` or
`localhost:8080`.  This change installs an in-process fake
:class:`HelixClient` substitute via a pytest autouse fixture so
the previously-live integration tests run without Docker.

#### Approach

The fake is **not** a subclass of `HelixClient` (that wouldn't
work because `HelixClient` is `@dataclass(slots=True)`, blocking
new instance attributes; also a subclass's overridden methods
would not fire on instances created before the patch).  Instead,
the fake is a **method-level patch** — every test run installs
fake implementations of `HelixClient.{close, health, is_available,
ping, execute, count_nodes}` via `monkeypatch.setattr` on the
class.  This works regardless of when the instance was constructed
and respects the slots constraint.

Per-instance state (an in-memory node store keyed by label, an
envelope log, error-injection points) lives in a class-level dict
keyed by `id(instance)`.  This is the standard workaround for the
slots + extra-state combination.

#### Step semantics

The fake implements the small subset of Helix query steps that
production code emits:

| Step | Fake behaviour |
|---|---|
| `AddN` | Append the unwrapped props to the label's bucket |
| `AddE` | Append to the edge label's bucket (no referential integrity) |
| `NWhere` | Filter the pipeline (or the whole store) by `field = value` |
| `Count` | Count the pipeline length, or all nodes if no prior step |
| `Drop` | Remove matched nodes (keyed by stable field-value tuple) |
| `Values` | Project fields; multi-field produces `{"properties": [...]}` (the shape `_list_nodes` consumes) |
| `Limit`, `N`, `SearchVector` | No-op pass-through |

#### Production code

No changes.

#### Test code

| File | Change | Reason |
|---|---|---|
| `tests_harness/__init__.py` (new) | Empty package marker | The harness code lives outside `tests/` because a third-party `tests` package in the venv (from an ML dep) shadows the local one |
| `tests_harness/fake_helix.py` (new) | The fake itself: method-level patches + per-instance state store + step walker | Replaces the real `HelixClient` for every test. Lives at the top level (not under `tests/`) so Python can resolve the import |
| `tests/conftest.py` | Added autouse `fake_helix_in_process` fixture that calls `install_fake(monkeypatch)` | Wires the fake in for every test without requiring any test file to opt in |
| `tests_harness/test_fake_helix.py` (new) | 18 tests: lifecycle, health, envelope validation, step semantics (count-after-NWhere, Drop, Values envelope), error injection, state isolation | Pins the fake's contract so a regression surfaces as a localised failure here, not as a wave across `test_memory_helix.py` and `test_kg_helix.py` |

The HelixDB skips were the **only** "is the sidecar up?" gate in

### 8.6 Evening: nightly cron + retention rotation

The nightly-eval plumbing (`scripts/nightly_eval.py`,
`scripts/regression_gate.py`) shipped with Phase 8 — the
scripts existed, the CLI behaviour was tested (`test_phase8_eval_drift.py`),
but there was no installable cron and no retention story. This
change wires the three-step nightly run into a hardened systemd
unit + timer and adds the retention rotation that prevents
`workspace/eval/` from growing without bound.

#### Approach

Three new files, all under the project root:

```
monitoring/
  nightly-eval.service    # Type=oneshot — runs the three scripts
  nightly-eval.timer      # OnCalendar=*-*-* 03:15:00 + Persistent=true
scripts/
  rotate_eval_reports.py  # Pure-stdlib retention helper
  NIGHTLY.md              # Install + operations doc
```

The service runs three Python scripts in sequence:
`nightly_eval.py --runner stub` → `regression_gate.py` →
`rotate_eval_reports.py`. Each step's exit code is captured in the
systemd journal. Steps 2 and 3 are best-effort (`|| true`) — a
regression-fail or a prune error must not block the next run.

#### Retention rotation: two layouts

The rotation script handles both layouts an operator might pick:

1. **Flat** — a single directory of `*.json` files. The script
   deletes any file whose `started_at` is older than the cutoff.
2. **Archived** — `archive/YYYY-MM-DD/nightly_report.json` per-day
   buckets. The script drops a whole bucket only when its newest
   report is older than the cutoff.

The layout is auto-detected (presence of subdirectories vs top-level
JSONs), so an operator can switch from one to the other by moving
files without changing the script invocation.

#### Unparseable reports are preserved, not deleted

A nightly report with a missing or malformed `started_at` is
**kept**, not pruned. The reasoning: a corrupt report is data we
want to look at later, not garbage we want to silently lose. The
test `test_unparseable_preserved` pins this contract.

#### systemd over cron

We picked a systemd timer over a `crontab` entry for four reasons
that matter for a self-hosted personal assistant:

* **Journal integration** — every run logs to the systemd journal
  with `SyslogIdentifier=raven-nightly-eval`; `journalctl -u
  raven-nightly-eval.service` shows the full history.
* **`Persistent=true` catches missed runs** — cron skips if the
  host was asleep; the timer catches up on next boot.
* **Hardened service unit** — `NoNewPrivileges`,
  `ProtectSystem=strict`, `ProtectHome=true`, `PrivateTmp=true` give
  us a sandbox for free that a crontab entry doesn't.
* **Three-step `ExecStartPost` chain** — the eval, the gate, and
  the rotation share one timer and one log stream.

A crontab fallback is captured as a comment in `scripts/NIGHTLY.md`
for non-systemd inits.

### 8.8 Late evening: Tauri shell scaffolding

#### Architecture

```
companion-shell/
  src/                          # vanilla HTML/CSS/JS — no bundler
    index.html                  # status tile + command palette + event log
    main.js                     # listens to Tauri events, invokes commands
    style.css                   # minimal stylesheet (system colors)

    Cargo.toml                  # tauri-runtime is opt-in

    build.rs                    # feature-gated tauri-build hook
    src/lib.rs                  # library entry; feature-gated run()
    src/protocol.rs             # wire types — mirror of app/companion/types.py
    src/client.rs               # WebSocket client + offline queue
    src/tauri_app.rs            # Tauri runtime (--features tauri-runtime)
    src/main.rs                 # binary entry point
```

The split between the library and the Tauri-specific code is the
load-bearing detail.  **The library builds and tests on any cargo
host** — no webkit2gtk, no Xcode.  The Tauri binary is gated
behind `cargo build --features tauri-runtime` so a CI on a host
without a desktop can still verify the wire-format half.

The Rust library has 26 unit tests covering:

* every `MessageKind` string matches the Python enum
* every wire frame round-trips through `Frame::from_json` / `Frame::to_json`
* the offline queue overflow drops the oldest frame (matches the
  Python `OfflineCache` semantics)
* the dispatch helper maps server-initiated frames onto the right
  `CompanionEvent` variant
* the `Status` shape is **flat** (not a nested `snapshot` dict) to
  match the Python dataclass field-for-field
* Hello's `platform` string is one of the five documented values,
  decided at compile time

The Python suite (`tests/test_companion_shell_wire.py`, 26 tests)
verifies the same wire contract from the other side: every
Python-emitted frame JSON parses cleanly under the Rust rules,
every Rust-emitted fixture parses cleanly under the Python
parser, and the `MessageKind` enums agree one-for-one.  A drift
between the two — a field renamed on one side, a kind added
without the other — fails at CI time on the language that
introduced the drift.

#### Frontend

The UI is deliberately minimal:

* **Status tile** — current CPU/RAM, queue depth, uptime, last
  action, last error.  Driven by `companion://status` events.
* **Command palette** — text inputs for `intent` + JSON `args`,
  submit posts a `Command` frame and shows the generated id in
  the event log.
* **Event log** — rolling list of the last 100 frames, colour-coded
  by kind (welcome = green, error = red, response = accent).
* **State badge** — top-right shows the current `ConnectionState`

```js
const id = await invoke("send_command", { intent: "set_mode", args: {mode: "offline"} });
```

#### Wire-format findings (and what was fixed)

Writing the cross-language tests caught one real bug: the **Rust
`Status` was originally a nested `snapshot` field** (more
ergonomic for the JS side), but the **Python `Status` is flat**
(field-per-attribute).  The wire contract has to match one side
exactly, so the Rust `Status` was changed to the flat shape.  The
JS side flattens it back into a nested object for rendering.

The fix is in `companion-shell/src-tauri/src/protocol.rs::Status`
and `src/client.rs::dispatch` (which now constructs a flat JSON
object for the JS frontend).  Without the cross-language tests,
this drift would have surfaced as a parse failure on the first
real WebSocket frame in production.

### 8.11 Late night: modular platform ↔ mother module integration options

The user clarified the J.A.R.V.I.S. vision: RAVEN is a single

This change wires the 8 Phase 3 routes into the FastAPI app so

#### Approach

Three pieces of glue, all inside `app/web/server.py`:

1. **Module-level pydantic body models** for the three POST
   endpoints that take JSON (`FinanceExpenseBody`,
   `FinanceBudgetBody`, `HealthReadingBody`).  These are defined
   at module scope (not inside `_build_app`) because FastAPI
   needs to resolve the type to a Body — `from __future__ import
   annotations` would otherwise make locally-scoped classes
   appear as `ForwardRef("FinanceExpenseBody")` and the dependency
   solver would reject them as 422.
2. **Eight route handlers** mounted inside `_build_app` after
   the static mount.  Each one is a thin adapter that:
   - Translates URL/path/query params into the kwargs the
     router's `dispatch(route, **kwargs)` expects.
   - Calls `life_router.dispatch(route, **kwargs)`.
   - Maps the result dict to an HTTP status code via
     `_http_status(result)`.
3. **`_http_status(result)`** — a single mapping that turns the
   router's `ok=False` error strings into HTTP codes:
   `amount_must_be_positive` → 400, `unknown_route` → 404,
   everything else → 500.  `ok=True` returns 200.

### 8.16 2026-06-20: Q2 from §6 design doc — at-least-once event delivery for `EventBridge`

Closed Q2 from
[`docs/12-modular-platform-integration.md`](docs/12-modular-platform-integration.md)
§6.  `EventBridge` was historically calling `OutputRouter.route(...)`
and `SentinelBridge.inject_event(...)` **synchronously** from inside
`_submit_raised` and `_record_history`; if the destination was
unavailable (process restart, outbox replay in flight, BotSignal
failure) the event was lost.  Now the external-sink delivery is
routed through the existing `Outbox` machinery so the bridge's
delivery is at-least-once and survives process restarts.

**Design choice: outbox+replay, not ack-on-publish.**  Rationale
spelled out in `.puku-cli/plans/misty-jumping-flame.md`; the short
version is that the pattern is already in the repo (the same
machinery `BotSignal.send` was routed through in §8.2), it
avoids head-of-line blocking on the surveillance use case, and it
survives process restarts.

**In-bridge detector/reaction fan-out is unchanged.**  The
synchronous `for detector in self._detectors_for(...)` loop in
`EventBridge.on_event` is the module-internal contract that
`HealthMonitor.guard` isolation depends on.  Only the
**external-sink** delivery (OutputRouter + SentinelBridge) is
wrapped.  This is explicitly a non-goal of the change.

**What shipped:**
- `app/runtime/event_outbox.py` (~280 lines) — thin wrapper
  around `Outbox` with the per-channel senders
  (`output_router`, `sentinel_bridge`) registered by the
  bridge.  Module-level singleton + env-var override
  (`RAVEN_EVENT_OUTBOX_PATH`).  Idempotency key built from
  `make_idempotency_key("event_bridge", module_id, source_name,
  event_id, sink)`.
- `app/modules/event_bridge.py` — `durable=True` (default)
  routes `_submit_raised` and `_record_history` through the
  outbox; the outbox sender is the **single delivery point**
  (no double-fire on success).  `durable=False` opts out for
  tests that need the pre-outbox synchronous contract.
- `tests/conftest.py` — new `isolated_event_outbox` autouse
  fixture mirroring `isolated_outbox`.
- `tests/test_event_bridge_durable_delivery.py` (9 new tests) —
  pins enqueue, drain-delivers, `durable=False` opt-out,
  idempotency-key collapse, drain-failure retry, two-sink
  independence, sentinel-payload shape, restart-survival, and

**Bug found and fixed during the work:** `Outbox.__len__` makes

## §8.21 — Phase 4 second module: LearningTracker (2026-06-20, v10)

**What:** Shipped `app/core/learning_tracker.py` — the second
of three Phase 4 modules specified in
`JARVIS_MILESTONE_PLAN.md` (Weeks 7-8).  `home_orchestrator.py`
remains for a future cycle.

**Design — read-only analytics facade:**

`LearningTracker` joins two existing data sources into a
single coherent view of "what the user has learned" and
"what tools fail most often":

1. `SkillLearner`'s `skills/learned/<slug>/module.yaml`
   inventory (one manifest per learned skill, recording
   `invocation_count`, `success_rate`, `confidence`, and
   `last_invoked`).
2. `AuditLog`'s `kind="tool_call"` events (one row per tool
   call, with `action` = tool name, `success`,
   `duration_ms`, `risk_level`).

The tracker is **stateless beyond configuration** — every
compute method walks the underlying sources on demand, so
the view is always real-time and there is no cache to
invalidate.  Five-method API:

* `compute_skill_profile(sort_by="invocation_count")` →
  `list[SkillRow]`
* `compute_tool_profile()` → `list[ToolRow]`
* `compute_learning_velocity(window_days=30)` → `int`
* `top_failure_modes(top_n=5)` → `list[FailurePattern]`
* `summary()` → `LearningSummary` (composes all four plus
  event-weighted `overall_success_rate` and a text render
  for `/learned`)

The tracker has **no fallback file**.  Unlike
`KnowledgeManager`, which carries a JSONL fallback for the
KG backend, the tracker's sources (manifests + audit log)
are themselves the canonical records.  When either is
missing, the relevant method returns an empty list and the
caller sees a zero-state summary.

Failure modes are silent — a missing audit log, a missing
skills directory, a broken manifest, or a malformed YAML
file all degrade to an empty result, never an exception.
The tracker is on the read path of the ambient loop and
the `/learned` slash command, and a crash would break both.

**Three integration points:**

1. **`app/core/learning_tracker.py`** (~440 lines, new) —

## §8.22 — Phase 4 third module: HomeOrchestrator (2026-06-20, v11) → Phase 4 🟢 COMPLETE

**What:** Shipped `app/core/home_orchestrator.py` — the third
and final Phase 4 module specified in
`JARVIS_MILESTONE_PLAN.md` (Weeks 7-8).  All three Phase 4
modules are now in (`knowledge_manager.py` v9 +
`learning_tracker.py` v10 + `home_orchestrator.py` v11).

**Design — missing high-level coordinator on top of the HA
wrappers:**

RAVEN already had the Home Assistant wrappers
(`SmartHomeTool`, `SensorReadTool`, `AirQualityTool`,
`CameraSnapshotTool`, `WeatherTool`) — all stateless, each
call hits the HA REST API and returns.  There was no
notion of "named, reusable, location-tied sequences of
calls" — and that is exactly the gap the orchestrator
fills.

**Two domain primitives:**

1. **`Scene`** — a named, ordered list of `SceneAction`s.
   Each action is ``(entity_id, service, service_data)``.
   A scene is *location-tied* (e.g. ``movie_mode`` lives
   in the ``living_room``).  The orchestrator's
   `current_scene_for_presence()` answers "what should the
   house be doing right now?" by joining the user's current
   location with the newest matching scene.

   ISO timestamp and a source tag (``"user"`` for explicit

## §8.23 — Hierarchical sub-plan execution in `PlanExecutor` (2026-06-20, v12)

**What:** Replaced the `NotImplementedError` in
`app/core/planning/executor.py` for `step.action == "subplan"`
with a recursive sub-plan executor.  This is the first
pick outside the Phase 1-4 backlog.

**The latent gap:**

The type system had already accepted `"subplan"` for
months:

* `app/core/planning/types.py` declares
  `StepAction = Literal["tool", "subplan", "llm", "ask_user", "wait"]`
* `goal_tracker.py` already produces sub-plans and tracks
  them under `goal.sub_plans`
* `cost_estimator.py` already estimates the cost of a
  sub-plan step (delegated to its children)

The planner *promised* the runtime it could dispatch
sub-plans — and the runtime was raising.  The type
system was effectively a lie.

**Design — six small additions:**

1. **`PlanStep.subplan_id: str | None`** — new optional
   field with full `to_dict` / `from_dict` round-trip.
   Old plan dicts that don't carry the field load with
   `subplan_id=None`, so this is backwards-compatible.

2. **`PlanExecutor.subplan_resolver`** — new injection
   point (`Callable[[str], TaskPlan | None]`, async
   variant supported).  The executor calls this with the
   step's `subplan_id` to fetch the referenced
   `TaskPlan`.  Returning `None` is a "sub-plan not
   found" error; raising is propagated.  This keeps the
   executor decoupled from `PlanStore` (avoids a circular
   import).

3. **`PlanExecutor.subplan_executor`** — optional
   injection point.  When set, sub-plans run through a
   *separate* executor instance (separate retry budget,
   separate checkpoint context, separate hook chain).
   When `None` (the default, also what tests use), the
   parent executor recurses into its own `execute()`,
   which is the right call for simple deployments.

4. **`PlanExecutor._dispatch_subplan`** — the actual
   dispatcher.  Resolves the sub-plan, runs it, and
   surfaces the result:
   * `COMPLETED` → the sub-plan's `subplan_result`
     metadata (if set by the planner), else the last
     completed step's result, else a
     `{"status": "completed", "subplan_id": ...}`
     summary.  This becomes the parent step's `result`.
   * `FAILED` / `ABANDONED` → raises a `_SubplanFailed`
     sentinel with the parent step id + the first failed
     sub-plan step's error.

5. **Retry-aware error handling.**  A failed sub-plan is
   a **non-retryable** terminal failure at the parent
   step level — the sub-plan already exhausted its own
   retry budget, so re-running it from the parent would
   just re-trigger the same failure and overwrite the
   first attempt's error with an identical copy on
   attempts 2 and 3.  The `_SubplanFailed` sentinel is
   caught at the top of `_run_step`'s retry loop and
   breaks out immediately, preserving the first
   attempt's error.

6. **Nested sub-plans** (sub-plan containing a sub-plan
   step) work via the same recursive path — the resolver
   is consulted for every sub-plan step in the chain.

**Test results:**

* 20 tests in `tests/test_planning_subplan.py`:
  * `TestPlanStepSubplanId` (3) — default, round-trip,
    backwards-compatible dict load
  * `TestSubplanHappyPath` (3) — last-step result
    propagation, single-step sub-plan, explicit
    `subplan_result` metadata override
  * `TestSubplanFailure` (2) — sub-plan failure fails
    parent step with informative error, parent plan
    reaches `PlanStatus.FAILED`
  * `TestSubplanErrorPaths` (8) — missing `subplan_id`
    (None + blank), missing resolver, unknown
    `subplan_id`, resolver returning non-plan, resolver
    raising, sub-plan with no steps, async resolver
    awaited
  * `TestNestedSubplans` (2) — sub-plan containing a
    sub-plan step, dedicated `subplan_executor` honoured
  * `TestSubplanIntegration` (2) — `on_step_complete`
    hook fires for subplan step, parent does not
    double-execute

* All 35 existing `tests/test_planning.py` tests still
  pass — this change is additive (a new step action + a
  new resolver field), not a refactor of existing
  behaviour.

* Full-suite baseline: **2501 passed, 2 skipped** (+20
  from v11's 2481).  Same pre-existing
  `test_audit_redaction.TestCustomConfig::test_extra_pattern`

**Gap-analysis impact:** Scorecard v11→v12 at **±0
capability delta** — the underlying planner and goal

**Cumulative v7→v12 picture:** 159 new integration

## §8.30 — `SkillCurator` unit-tested — wiring half deferred (2026-06-21, v19)

The orphan scan from the v18 follow-on flagged
`app/core/skill_curator.py` (377 lines, zero
importers, zero tests pre-v19) as the next clean
pick.  The curator auto-scores, prunes, promotes,
and imports skills across three on-disk roots:

* **`skills/learned/`** — user-learned skills
  (Phase 9 outcome).
* **`skills/imported/`** — Hermes (agentskills.io)
  and OpenClaw imports.
* **`skills/.archived/`** — pruned-skill
  graveyard, with date-stamped entries
  (`<slug>_<YYYYMMDD>`).

A fourth root, **`skills/bundled/`**, is iterated
by `_iter_skill_dirs` but is **not** auto-created
by `__init__` — the iter silently skips a missing
root, so the curator works without it.  This is a
latent invariant, not a bug.

`SkillCurator(project_root=None, min_invocations_for_prune=5,
prune_threshold=0.3, promote_threshold=0.85,
promote_min_invocations=10)` exposes five
responsibilities:

1. **`score_all()`** — composite score formula
   `min(1.0, 0.35*confidence + 0.50*success_rate
   + min(0.15, log1p(invocations) * 0.03))`,
   sorted descending.  Results carry 9 fields:
   `module_id`, `name`, `score`, `success_rate`,
   `invocation_count`, `confidence`, `stability`,
   `origin`, `path`.
2. **`prune()`** — archives skills with
   `invocation_count >= min_invocations_for_prune`
   AND `success_rate < prune_threshold` (strict).
   The archive dir is
   `skills/.archived/<slug>_<YYYYMMDD>`.
3. **`promote()`** — flips skills with
   `invocation_count >= promote_min_invocations`
   AND `success_rate >= promote_threshold`
   (inclusive — opposite of prune) to
   `stability=stable` + `promoted_at=<ISO>`.
4. **`import_hermes_skill(source_dir)`** /
   **`import_openclaw_skill(source_dir)`** —
   format-aware external imports.  Both tag
   `origin=hermes|openclaw`, `trust_level=community`,
   `imported_at=<ISO>`.  Hermes preserves the
   source filename (`module.yaml`/`module.yml`/
   `manifest.json`); OpenClaw builds the canonical
   14-field `module.yaml`.
5. **`garbage_collect()`** — removes dirs with no
   manifest (`module.yaml` / `module.yml` /
   `manifest.json` / `SKILL.md`).

code changed.**  50 new tests in

* **`PerceptionEngine(workspace_dir=None)`** —
  lazy-imports `Config`, defaults
  `workspace_dir` to `Config.MEMORY_ROOT` when
  omitted, constructs an `AgentReach()` instance

* **`add_topic(query, interval_seconds=3600)`** —

  saves only when something was actually removed.

  whitespace, newline at end).

  `now - last_checked >= interval_seconds`;
  skip non-active topics; update `last_checked`
  to `time.time()`; save topics file only when
  something was actually updated.
* **`_sweep_topic(topic)`** (async) — calls
  `self.reach.discover(query, limit=5,

  `snippet` from each result with fallbacks
  (`url`→`source_url`→`"unknown"`,
  `title`→`name`→`"untitled"`,
  `snippet`→`content`→`""`), skips empty-snippet
  items, applies a keyword sentiment heuristic,
  truncates the snippet to 500 chars, builds an
  `EvidenceItem` and calls `save_evidence`.
  Swallows all exceptions from `discover`.

detection surface — scans user
context (tasks, sessions, history)

suggestions.

**Public API surface.** `Opportunity`
is a `@dataclass(slots=True)` with
7 fields: `opportunity_type` (one of
`deadline` / `automation` / `followup`
/ `info_gap` / `pattern`), `title`,
`description`, `confidence` (0-1),
`urgency` (one of `low` / `medium` /
`high` / `critical`), `suggested_action`,
`context` (dict), and `detected_at`
(ISO ts).

`OpportunityDetector(workspace_dir=None)`
defaults `workspace_dir` to
`Config.MEMORY_ROOT` when None or
empty string (both falsy).  `detect_all()`
runs the 5 sub-detectors in order

highest-confidence comes first,

**The 5 sub-detectors** (all swallow

`except Exception` + `logger.debug`):

  3600` hours — <24h → critical,

* `_detect_followup_opportunities()`
  lazy-imports `SessionManager`,
  iterates sessions dir for
  `<user_id>*.jsonl` files modified

  "when you get a chance" /
  "you might want to" / "consider" /
  "next steps" / "follow up" /
  "remind"), emits one
  `Opportunity(opportunity_type=
  "followup", urgency="low",
  confidence=0.6)` per session.

* `_detect_pattern_opportunities()`
  lazy-imports `TaskLedger`, lists
  tasks with `status="done"`,
  `Counter`s the lowercased titles,
  flags any title with 3+ occurrences

  urgency, 0.7 confidence).

* `_detect_automation_opportunities()`
  lazy-imports `TaskInboxStore`,
  iterates `_get_active_users()`,
  lists items with `kind="task"`,
  matches each title against 7

  `automation` Opportunity (low
  urgency, 0.5 confidence).

### 8.44 2026-06-21: v33 voice-stack refactor — whisper.cpp STT + Piper-TTS autherRaven personality + SinkRegistry fan-out

**Goal**: replace the v32 hybrid voice stack (`faster-whisper` CTranslate2 STT + `edge-tts` cloud TTS + inline `sounddevice.play`) with a fully-local v33 stack (`pywhispercpp` C++ inference + `piper-tts` ONNX personality voice named **autherRaven** + `SinkRegistry` fan-out dispatcher).  The v33 stack makes TTS play simultaneously through every registered sink for a user — the local sound card, the dashboard browser WS, and any future edge node — and removes the cloud round-trip on every reply.

**What landed:**

| Output devices | local sound card only | local + browser WS + future edge |

**The autouse `_stub_voice_engines` fixture** in `tests/conftest.py` ensures the 57 new tests run hermetically: monkeypatches `_get_whisper_cpp_model` to a counting class, monkeypatches `PiperTTS._ensure_loaded` to a stub `voice` whose `synthesize(text, file_obj)` calls `setnchannels/setsampwidth/setframerate/writeframes` directly on the pre-opened `wave.Wave_write`, sets `WHISPER_CPP_OFFLINE=1`, resets the sink registry / whisper cache / piper cache on teardown.

**The stub WAS wrong in v32**: the v32 autouse stub opened `file_obj` again with `wave.open("wb")` inside `synthesize`.  This failed with `# channels not specified` because the underlying stream was already in WAV-write mode (Piper's API expects to receive an already-opened `wave.Wave_write`, not a raw file).  The v33 stub mirrors the real `piper.PiperVoice.synthesize` API exactly — it sets channels/width/rate on the pre-opened writer and calls `writeframes` directly.  This was the missing piece in the v32 cycle that surfaced as the `# channels not specified` warning during the v32 tts test pass.

**The `os.unlink` race fix**: `SinkRegistry.play(audio_path)` reads the file into bytes *once*, then dispatches to every sink in parallel via `asyncio.gather`.  The unlink now happens *after* the read but *before* the dispatch — closing the race where a slow sink could read a tempfile that a faster caller had already unlinked.

**Backward compatibility**:
- `synthesize(text, voice=None) -> str` (file path) preserved
- `Config.VOICE_TTS_VOICE` legacy BCP-47 strings emit a one-time `DeprecationWarning` and fall back to the default voice
- `sounddevice` still used for the on-device sink; only the invocation point moved from `pipeline._speak_streaming` to `LocalSoundDeviceSink.play`
