**Date:** 2026-03-01  
**Codebase revision analysed:** current HEAD

## 1. Executive Summary

SARAS has a solid, working skeleton: three platform connectors (Telegram, Discord, Slack), a two-layer reasoning engine (MiniEngine + AgentRuntime ReAct loop), a swarm of 8 specialist agents, 30+ tools, rich-text rendering for all three platforms, and a file-based memory system. The foundation is production-quality Python.

However, the gap between "working bot" and "real-life Jarvis" is large. The docs describe 7 architectural layers; only layers 1 and 3 (connectors and brain) are substantially implemented. Voice, sensors, smart home, persistent semantic memory, scheduling, a web dashboard, local LLMs, fine-tuned personality, and operational infrastructure are all either absent or exist only as stubs.

**Rough completeness estimate: ~28% of the full Jarvis vision.**

## 3. Gap Analysis — Everything Needed for Real Jarvis

### 3.1 Voice System — **~15% done**

The vision is: wake word → STT → brain → TTS → speak back on whichever platform the user spoke from.

**What exists:**
- `app/voice/` directory with `deep_gram.py`, `google.py`, `piper.py`, `voicefunc.py`, `voicetool.py`
- Vosk offline model (`vosk-model-small-en-us-0.15/`) bundled
- Piper TTS ONNX model (`en_US-lessac-medium.onnx`) bundled
- `pvporcupine`, `openwakeword` installed in `pyproject.toml`
- `pyaudio`, `sounddevice` installed
- `DEEPGRAM_API_KEY`, `API_KEY_SPEECHMATE` in config
- `saras_voice.py`, `test_wakeword.py`, `test_pipewire_source.py` exist at root

**What is missing / not wired:**
- [ ] Voice pipeline is **not integrated** into `main.py` or `MessageOrchestrator` — it's standalone scripts only
- [ ] No STT preprocessing for Telegram/Discord voice notes in the main flow (voice notes arrive as files; the bot does not transcribe them automatically)
- [ ] Wake-word detection loop not running as an asyncio task in the main bot
- [ ] No `VoiceIOConnector` class that mirrors the DiscordBot/SlackBot pattern
- [ ] Piper TTS not generating `.ogg` for Telegram voice replies or `.opus` for Discord
- [ ] No microphone input loop for local server speaker (the `live.py` script is standalone)
- [ ] No VAD (Voice Activity Detection) integration — start/stop recording on speech
- [ ] Discord voice channel joining (`discord.VoiceClient`) not implemented in `discordapp.py`
- [ ] XTTS v2 (cloned voice) not installed — only Piper available
- [ ] faster-whisper not installed — only Vosk (lower quality) is bundled

**What to build:**
1. `app/voice/pipeline.py` — unified async voice pipeline: mic → VAD → STT → brain → TTS → speaker
2. Wire voice pipeline as a task in `main.py` alongside Telegram/Discord/Slack
3. Handle Telegram/Discord voice note downloads → STT → treat as text request
4. Generate TTS audio files and send back as `payload.audio_path` through `BotSignal`
5. Implement Discord voice channel joining and real-time audio streaming
6. Implement wake-word loop with porcupine/openwakeword on server microphone

### 3.2 Memory — **~20% done**

The vision is: semantic long-term memory using pgvector, per-user facts, preferences, past events.

**What exists:**
- `MemoryTool` appends text to `workspace/AGENTS.md` and `workspace/TOOLS.md` — flat Markdown files
- `SessionManager` keeps last 50 turns in JSONL per user (conversation history only)
- `Bootstrapper` reads SOUL.md, AGENTS.md, TOOLS.md and injects them into the system prompt
- `KnowledgeGraphTool` uses Neo4j for structured relationship storage

**What is missing:**
- [ ] **No vector database / semantic search** — memory retrieval is "inject everything" not "retrieve relevant"
- [ ] No PostgreSQL + pgvector setup (described in docs as the target)
- [ ] `AGENTS.md` / `TOOLS.md` will grow unbounded — no pruning, no summarisation
- [ ] No user profile table (preferences, timezone, name, platform IDs)
- [ ] No memory importance scoring or forgetting curve
- [ ] No cross-session "did the user mention X before?" lookup
- [ ] No embedding model running (sentence-transformers not installed)
- [ ] Neo4j is optional / manually deployed — not part of `main.py` startup

**What to build:**
1. Add `sentence-transformers` (or use an embeddings API endpoint) to `pyproject.toml`
2. Create `app/core/memory.py` — `MemoryStore` using pgvector or ChromaDB (lighter option)
3. On every turn: retrieve top-5 semantically relevant memories and inject them
4. `MemoryTool.save_memory()` should write to the vector store, not just a flat file
5. Periodic background task to summarise and prune old sessions
6. User profile model in SQLite or PostgreSQL

## 6. Key Technical Decisions to Make

Before Phase 3–6, these architectural choices need to be locked in:

1. **Memory backend**: ChromaDB (embedded, zero-ops) vs. pgvector (PostgreSQL, more powerful) — ChromaDB is recommended for Phase 2, migrate to pgvector in Phase 5.

2. **Local LLM**: Ollama (easiest) vs. vLLM (highest throughput, needs GPU) — Ollama first, vLLM if a GPU server is available.

3. **WhatsApp approach**: Baileys (Node.js, free, unofficial) vs. WhatsApp Business API (official, paid, requires business approval) — Baileys for personal use.

4. **Voice STT quality**: Vosk (offline, bundled, mediocre) vs. faster-whisper (better quality, ~1 GB model) vs. Deepgram API (best quality, paid) — faster-whisper locally is the sweet spot.

5. **Streaming**: Telegram edit-based streaming works but is visually janky. Discord has a better UX for this. Decide whether streaming is a UX priority.

6. **Deployment target**: bare-metal Raspberry Pi / home server vs. VPS vs. cloud — this affects which services (vLLM, MQTT broker, cameras) are feasible.

## 7. What Makes This Feel Like Jarvis

The single biggest differentiator between "a good chatbot" and "Jarvis" is **proactive, environment-aware behaviour**. Currently SARAS only responds when spoken to. Jarvis:

- Tells you about your meeting 15 minutes before it starts (scheduling)
- Alerts you when the door sensor fires at 2 AM (sensors)
- Says "good morning" and reads you the news (routines)
- Answers when you call its name (wake word)
- Speaks to you in a recognisable voice (TTS personality)
- Remembers what you said last week and refers to it naturally (semantic memory)

The code infrastructure to support all of this exists in partial form. The path from here to Jarvis runs directly through Phases 2 and 3 above.
